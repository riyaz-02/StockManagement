# Data model (essentials)

**One database** (the website's `shopmanage`; locally `lgp_dev`), see `docs/DB_UNIFICATION.md` for who owns which collection. The website's shape is the master for the shared collections:
- `users` = ONE list of people for the app and the website. Stored with the website's field names (`username`, `email`, `password`, `full_name`, `role`, `contact`, `is_active`, `status`, `created_at` ...); the app adds `mobile`, `branchId`, `branchName`, `permissionOverrides`, `language`, `fcmTokens`, `legacyAppIds`, `source`. `models/User.js` aliases the app's old names (`name`, `isActive` ...) to the stored ones. One password hash works on both sides.
- `purchases` = ONE list for the app and the website, stored in the website's shape (`models/Purchase.js`: `invoice_date` text, `invoice_number`, `metal_type` 'Gold', `total_amount` incl. GST ...) with the app's GST split / valuation as extra fields; old website purchases show no GST (`gstRecorded:false`).
- `customers` = the website's customers, found by any of 4 numbers and created the website's way through `services/customerStore.js`; the app's extras (customer code, wishlist, bookings, richer details) live in `app_customer_profiles`.
- App-only: items, containers, tallysessions, bookings, notifications, outwardmovements, repairlogs, rolepermissions, inventorysnapshots, appversions, scheduledjobstates (Mongoose models in `backend/models/`), `app_settings` (was `settings`), `app_trash` (copies of records removed from shared collections), `bulk_weights` (bulk stock: dust, parts, sub-items, raw, in-process, reserved; `category`, `purity`, `pieces`), `gst_configs`, and the app-owned `app_request_locks` (idempotency) · `app_audit_log` · `app_gst_settings` · `app_gst_reminder_log` · `app_branches` · `app_customer_profiles` · `app_counters`.
- **Stock = what is in the shop** (`items` present + active `bulk_weights`); there is no hand-kept stock ledger. The reconciliation and daily summary come from `purchases`, `app_old_metal`, `invoices` (non-cancelled bill lines) and the website's `wastage_reports` (approved). The website's own `stock_entries` (its manual Credit / Debit ledger) is left as it is for the old site and is not used by the app.
- **Purchases** also carry `roundOff` and `calculatedPayable` (app fields): `total_amount` / `totalPayable` is the supplier's printed total, `calculatedPayable` what the rules worked out; GST and ITC come from the taxable value.
- **Stock Summary** uses `daily_snapshots` (website's shape: `date`, `gold`/`silver` {purchase_total, calculated_purchase, stock_total, expected_stock_debit, total_sold, final_result, discrepancy_percentage}; the app adds fields beside them and `basis:'items'`, old website snapshots have no basis = hand-kept ledger) and `wastage_reports` (website's shape: `wastage_date`, `metal_type`, `wastage_amount`, `category`, `reason`, `status`, `reported_by`, `approved_by`, `admin_comments`). Settings: `app_stock_settings.reconcile`. See `docs/STOCK_SUMMARY.md`.
- **Filed GST returns = the website's `gst_data`**, one document per financial-year quarter (`financial_year` = the year the FY starts, `quarter` 1-4); the website's flags (`gstr1_filed`, `gstr3b_filed`, dates, `gst_paid`, `itc_amount`) are kept in step and the app's richer records (ARN, amounts, PMT-06, GSTR-9, monthly and branch-GSTIN returns) sit in the same document as `filings: [...]` (`services/gstFilings.js`).
- **Generated GST records = the website's `outputDoc`** (`document_id`, `document_name`, `document_type` GST_MONTHLY_REPORT, `generation_timestamp`, `month`, `year`, totals ...); the app writes one row per record in the website's shape.

**Branches:** `app_branches` (name, prefix, state, optional own `gstin`), `users.branchId`. Stock/ops models (Item, Container, TallySession, Booking, RepairLog, OutwardMovement, InventorySnapshot, Purchase, BulkWeight) carry `branchId` (missing = `main`), stamped and filtered automatically by `utils/branchScope.js`. Invoices carry `branch_id`/`branch_name`. **Registrations** (`services/registrations.js`): the default GSTIN covers main + branches without a GSTIN; a branch with its own valid GSTIN is a separate registration. `app_gst_settings.key` = `main` | `gstin:<GSTIN>`; a filing's `gstin` ('' = default registration) with (gstin, returnType, period) unique, enforced by `services/gstFilings.js`.

**Website collections in the one database** (**prod is read + guarded insert only**): `invoices` (snake_case), `shop_info` (numbering counters, seller GSTIN/state).
Invoice fields the app writes beyond the website's: `hallmark_total` (hallmark / HUID fees passed on after tax, rule v3: inside `total_amount` / payable, outside `gst_summary`; each such line carries `hallmark_charge` + `hallmark_in_taxable:false`, its `total` = taxable + GST + fee), `discount_mode` ("before_gst" | "after_gst"), `discount_given`, `discount_before_gst`, `gross_taxable`, `bill_before_discount`, `metal_value`, `gst_type` (CGST_SGST | IGST), `seller_gstin`, `supply_state_code`, `additional_charges_gst`, `payments[]`/`payment_history`. Line fields: `certification`, `hallmark_charge`, `huid`, `item_name`, `extras`, `stone_charge`, `purity`, `gross_wt`, `product_code`, `item_id`.
Item optional billing detail: `grossWeight`, `lessWeight`, `stoneValue`, `stoneNote`, `makingCharge`, `supplier`, `size` (null/'' = not set). Conversion doc↔API shape: `services/billingView.js` (`toView`, `toRow`).


Legacy invoices (website-made) use `discount_mode` absent → treated as `after_gst`; never rewrite them.
